# Project Management Service (FastAPI)

## 📌 Overview

Backend-сервис для управления:

- пользователями
- проектами
- задачами
- комментариями

Реализован с использованием:

- FastAPI
- SQLAlchemy (async)
- PostgreSQL
- Pydantic

Проект создан как практическая тренировка backend-разработки с упором на:

- архитектуру слоёв
- работу с ORM
- обработку ошибок
- построение CRUD API

---

## 🏗 Архитектура

Проект разделён на слои:

```
API (routes)
↓
Service (бизнес-логика)
↓
Repository (работа с БД)
↓
Database (SQLAlchemy)
```

### 📌 Ответственность слоёв

#### API

- принимает запросы
- валидирует входные данные
- возвращает response_model
- преобразует ошибки в HTTP

#### Service

- содержит бизнес-логику
- управляет транзакциями
- вызывает репозитории
- выполняет проверки

#### Repository

- содержит только SQLAlchemy-запросы
- не содержит бизнес-логики
- работает с ORM моделями

- User → Project

## ⚙️ Ключевые решения

### 1. Асинхронный SQLAlchemy

Используется async session + asyncpg драйвер.

### 2. Разделение слоёв

Repository не знает о бизнес-логике, Service не знает о HTTP.

### 3. Dependency Injection

Используется только для:

- DB session (в API)
- сервисов (в API)

Репозитории создаются внутри сервисов.

---

## ⚠️ Основные проблемы, с которыми столкнулся

### ❌ 1. Неправильное использование HTTPException

**Проблема:**

```python
return HTTPException(...)
```

**Решение:**

```python
raise HTTPException(...)
```

---

### ❌ 2. Несоответствие response_model

FastAPI валидирует ответ → если вернуть не тот формат:

```
ResponseValidationError
```

**Причина:**

- возвращался не тот тип (например, объект вместо списка)
- возвращался None

---

### ❌ 3. Ошибки SQLAlchemy (типизация)

Ошибка:

```
integer = character varying
```

**Причина:**

- поиск по id, но передавался email

---

### ❌ 4. Непонимание flush vs commit

**Фикс:**

- `flush()` — получить ID до commit
- `commit()` — фиксирует транзакцию

---

### ❌ 5. Время создания (created_at)

**Было:**

```python
datetime.utcnow()
```

**Стало:**

```python
func.now()
```

👉 перенос логики на уровень БД

---

### ❌ 6. PATCH vs UPDATE

Проблема:

- update требовал все поля

Решение:

```python
model_dump(exclude_unset=True)
```

---

### ❌ 7. Слабое понимание SQLAlchemy запросов

Основная проблема проекта:

- сложность написания запросов
- отсутствие уверенности в join'ах
- риск N+1

👉 требует отдельной практики

## 🧪 Что реализовано

- CRUD для всех сущностей
- базовые связи между моделями
- обработка ошибок
- валидация через Pydantic
- асинхронная работа с БД

---

## 🚧 Что НЕ реализовано (осознанно)

- пагинация
- фильтрация
- сортировка
- оптимизация запросов
- защита от N+1
- аутентификация (JWT)
- кэширование (Redis)

👉 будет добавлено после прокачки SQLAlchemy

---

## 📚 Выводы

1. Архитектура слоёв понятна, но требует практики
2. SQLAlchemy — основной bottleneck
3. Ошибки чаще всего:
   - типы
   - response_model
   - неправильные запросы

4. Без уверенного владения ORM нельзя масштабировать проект
